======================================================================
1. EXECUTIVE SUMMARY
======================================================================

GitStack is a mission-based Git learning and collaboration platform where
students first learn Git in a safe environment, then form teams, follow
real-world software-development workflows, and have their work automatically
evaluated by the system.

GitStack's complete learning journey is:

Learn Git
    -> Practise Safely
    -> Work in Teams
    -> Follow a Real Workflow
    -> Receive Automatic Assessment

The project will not attempt to build another GitHub. GitStack will use a
controlled Gitea server for student collaboration missions and will assess how
students use issues, branches, commits, Pull Requests, reviews, tests, merges,
and conflict resolution.

The development team will use GitHub, GitHub Issues, GitHub Projects, Pull
Requests, code reviews, and GitHub Actions while building GitStack. Gitea will
be an internal component of the finished GitStack learning environment.

Final recommendation:

Keep the original team roles, learning strategy, and milestone idea, but use
this revised nine-week sequence, reduced MVP scope, early collaboration
prototype, real Gitea workflow, and GitHub-based project-management process.

======================================================================
2. PROJECT PROBLEM
======================================================================

Many CSE students understand Git commands only at a theoretical level. They
often do not get a safe place to practise real collaboration activities such
as:

- Creating and managing branches
- Writing meaningful commits
- Connecting issues with code changes
- Creating Pull Requests
- Reviewing another developer's work
- Requesting and applying changes
- Resolving merge conflicts
- Following a professional team workflow

Existing tutorials usually check whether a student entered a command, while
traditional autograders usually check only whether the final code passes
tests. They rarely assess how the student and the team produced that code.

GitStack addresses this gap by evaluating both the final result and the
software-development workflow used to produce it.

======================================================================
3. PROJECT VISION AND UNIQUE VALUE
======================================================================

GitStack combines four core layers:

1. Learning and mission system
2. Safe Docker practice environment
3. Gitea-based team collaboration
4. Automatic workflow assessment

Traditional Git learning platform:

"Did the student enter the expected command?"

Traditional code autograder:

"Does the final code pass the tests?"

GitStack:

"What did the student build, how did the student build it, how did the team
collaborate, and did they follow the required professional workflow?"

GitStack will evaluate:

- Final repository state
- Branch and commit history
- Issue-to-Pull-Request connection
- Individual contributions
- Review activity
- Test results
- Merge discipline
- Conflict-resolution result
- Complete team workflow

6. KEY PRODUCT DECISIONS
======================================================================

6.1 Validate repository state, not exact commands

The assessment engine should not require one exact Git command when several
valid commands can produce the same result.

Example:

git checkout -b feature

and:

git switch -c feature

can both create the required branch. The validator should therefore inspect
the repository state, history, and workflow events rather than matching a
single command string.

6.2 Use real Gitea collaboration features

Gitea will provide:

- Repository hosting
- Issues
- Pull Requests
- Review comments
- Approvals and requested changes
- Merge operations
- Webhooks and activity data

GitStack will provide:

- Mission instructions
- Student role instructions
- Links to the relevant Gitea resources
- Activity summary
- Automated assessment
- Bangla feedback
- Individual and team reports

The team must not spend the MVP period rebuilding Gitea's Pull Request and
review interfaces.

6.3 Give every student a separate workspace

Each student must have an isolated container and an independent clone of the
team repository. Three students must never share one working directory.

Student A container ---\
Student B container ----> Gitea team repository
Student C container ---/

6.4 Make the collaboration scenario deterministic

The merge conflict must be deliberately created through a prepared repository
and predefined edits. The demonstration must not depend on a random conflict.

6.5 Use rule-based scoring for the MVP

Simple, transparent rules are more practical than AI grading for the first
version. Rules may check minimum commit-message length, issue references,
required Pull Request sections, required commits, review timing, and test
status.

11. GITHUB-BASED DEVELOPMENT AND PROJECT MANAGEMENT
======================================================================

11.1 Tool roles

GitHub Repository:
Stores the GitStack source code.

GitHub Issues:
Stores development tasks, feature requests, bugs, and documentation work.

GitHub Projects:
Tracks weekly progress, priorities, assignments, and status.

GitHub Pull Requests:
Supports code review, discussion, checks, and merging.

GitHub Actions:
Automatically runs linting, tests, and builds.

Gitea:
Provides the controlled Git collaboration environment inside GitStack student
missions.

Important distinction:

The team develops and manages GitStack on GitHub.
GitStack uses Gitea internally for student collaboration practice.

The team does not need Jira unless the faculty specifically requires it.
Maintaining Jira and GitHub Projects together would duplicate tasks.

11.2 GitHub Project board

Project name:

GitStack Development

Recommended statuses:

- Backlog
- Ready
- In Progress
- Code Review
- Testing
- Done

Use a Blocked label or field for blocked tasks. Do not create an unnecessarily
complex workflow.

11.3 Recommended issue categories

- Feature
- Bug

- Documentation
- Security

Recommended labels:

- frontend
- backend
- sandbox

11.4 Issue requirements

Every issue should contain:

- Clear title
- One responsible owner
- Reviewer
- Expected completion date
- Priority
- Estimated effort
- Acceptance criteria
- Related milestone
- Technical notes when necessary

Example:

Issue #12: Connect browser terminal

Owner: Member 1
Reviewer: Member 3
Milestone: Week 1 - Technical Prototype

Acceptance criteria:

- Terminal opens successfully
- Commands reach the backend
- Output appears in the browser
- Disconnection displays a useful error
- Another member reviews the code

11.5 Standard development workflow

Create Issue
    -> Assign Member
    -> Move to Ready
    -> Create Feature Branch
    -> Commit and Push
    -> Open Pull Request
    -> Move to Code Review
    -> Teammate Reviews
    -> CI Tests Pass
    -> Move to Testing
    -> Merge into Main
    -> Issue Closes
    -> Move to Done

11.6 Repository rules

- Never push directly to main
- Create one issue for every meaningful task
- Use one feature branch per issue
- Connect each Pull Request to its issue
- Require another member to review each Pull Request
- Pass applicable tests before merging
- Resolve review comments before merging
- Delete merged feature branches
- Update documentation when behavior changes
- Keep main in a working state

11.7 Branch naming

feature/12-browser-terminal
feature/18-gitea-integration
fix/24-terminal-disconnection
test/31-mission-validator
docs/40-api-documentation

Avoid unclear names such as:

rafi-work
new-feature
test123
final-code

11.8 Commit naming

Examples:

#12 Add terminal WebSocket connection
#12 Display terminal output
#12 Handle terminal connection failure

Commits should be focused and meaningful. Avoid messages such as update, fix,
work, change, or final.

11.9 Pull Request format

Title:

#12 Implement browser terminal connection

Description:

Related issue:
Closes #12

Changes:
- Added browser terminal
- Connected WebSocket
- Added error handling

Testing:
- Tested normal commands
- Tested disconnection
- Tested terminal restart

Checklist:
- Build passes
- Tests pass
- Documentation updated
- Teammate reviewed

11.10 Review rotation

- Member 1's Pull Requests: Member 2 reviews
- Member 2's Pull Requests: Member 3 reviews
- Member 3's Pull Requests: Member 1 reviews

Cross-component changes should also be reviewed by the member responsible for
the affected component.

11.11 GitHub Actions checks

The initial CI workflow should run on Pull Requests and main-branch updates:

- Install dependencies
- Run linting
- Run unit tests
- Build frontend
- Build backend

Sandbox and full Gitea integration tests may run locally if the hosted CI
environment cannot safely support them. Their results should still be recorded
in the Pull Request.

- Another member reviewed the code
- Relevant automated tests pass

- Error handling exists
- Database migration is committed when required
- Documentation is updated
- The feature works in the integrated application
- No known critical regression remains
- The linked Pull Request is merged

Do not report progress only as "80% complete." Use:

- DONE
- IN PROGRESS
- BLOCKED
- NOT STARTED

17. MAIN RISKS AND FALLBACKS
======================================================================

Risk: Interactive terminal does not work reliably
Prevention: Build the prototype in Week 1
Fallback: Use a command-by-command console

Risk: Gitea integration is more complex than expected
Prevention: Test API repository creation and webhooks in Week 1
Fallback: Use a manually seeded Gitea repository for the demonstration

Risk: Sandbox security is insufficient
Prevention: Use non-root user, resource limits, timeouts, and no host mount
Fallback: Run only in a controlled local environment

Risk: Merge conflict does not occur reliably
Prevention: Use prepared branches and predefined conflicting edits
Fallback: Use pre-created conflict branches

Risk: Assessment rules become too complex
Prevention: Use deterministic rules and one collaborative mission
Fallback: Reduce the rubric to essential workflow checks

Risk: Schedule delay
Prevention: Demonstrate weekly and freeze features on 15 September
Fallback: Remove badges, charts, exports, and optional polish

Risk: A member becomes unavailable
Prevention: Assign a backup owner to every critical component
Fallback: Pair on sandbox, Gitea integration, and assessment tasks early

Risk: GitHub and project board are not maintained
Prevention: Update issues and statuses as part of the Definition of Done
Fallback: Reserve 15 minutes at the end of each team meeting for updates

19. WEEKLY TEAM PROCESS
======================================================================

At the start of each week:

1. Review the previous demonstration.
2. Select the week's issues.
3. Confirm each issue's owner and reviewer.
4. Confirm dependencies and acceptance criteria.
5. Move selected issues to Ready.

During the week:

1. Move started issues to In Progress.
2. Create one branch per issue.
3. Commit small, meaningful changes.
4. Open Pull Requests early.
5. Review another member's work.
6. Keep the GitHub Project current.
7. Record blockers immediately.

At the end of each week:

1. Merge reviewed work.
2. Run the integrated system.
3. Demonstrate the planned outcome.
4. Record bugs and unfinished work as issues.
5. Update documentation.
6. Prepare evidence for faculty review.
7. Plan the next week using the actual project state.

Tasks should usually be small enough to complete in one or two days. Avoid
large issues such as "Build the entire backend." Split them into authentication
API, user model, role authorization, validation, and tests.

======================================================================
20. SUCCESS CRITERIA
======================================================================

The MVP is successful when this complete flow works reliably:

1. A student logs in.
2. The student completes an individual Git mission.
3. Commands run in an isolated container.
4. GitStack validates repository state.
5. The student receives Bangla feedback and progress.
6. An instructor assigns three students to a team mission.
7. GitStack creates a Gitea team repository.
8. Each student works from a separate container and branch.
9. The team uses an issue, commits, Pull Request, review, requested changes,
   tests, approval, merge, and controlled conflict resolution.
10. GitStack produces automatic individual and team assessment results.

The project's quality should be measured by this complete working flow, not by
the total number of pages or features.

======================================================================
21. FINAL PROJECT PITCH
======================================================================

GitStack is a mission-based Git learning and collaboration laboratory where
students first learn Git and GitHub-style workflows in safe practice
repositories. They then work as a real student team to complete issue, branch,
commit, Pull Request, code-review, testing, and merge-conflict missions. The
system evaluates not only the final code but also the complete collaboration
workflow, and provides Bangla feedback, individual scores, and team-performance
reports.

Short version:

Learn Git -> Practise Safely -> Work in Teams -> Follow Real Workflow -> Get
Automatically Assessed

======================================================================
22. FINAL DECISION
======================================================================

The original GitStack plan has a good foundation, but it should not be followed
without changes. The strongest and most realistic approach is:

- Keep the three-member responsibility structure
- Use the revised nine-week schedule
- Prove terminal, Docker, and Gitea risks in Week 1
- Build the first complete individual mission by Week 3
- Start collaboration before the 50% update
- Use real Gitea issues, Pull Requests, and reviews
- Keep the MVP to one polished collaborative mission
- Use deterministic repository-state and event validation
- Use GitHub Projects instead of duplicating work in Jira
- Maintain GitHub Issues, branches, Pull Requests, reviews, tests, and releases
- Freeze features after 15 September
- Use the final week for testing, deployment, and documentation

This approach gives the team a realistic workload and gives faculty members
clear evidence of both a strong project idea and a professional Software
Engineering development process.
