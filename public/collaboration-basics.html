Your Level 4 path

Receive a role → accept an issue → create a branch → push commits → open a Pull Request → review → update → test → merge.

01

How GitStack team missions work

An instructor assigns three students to a prepared mission. Every student receives a separate sandbox and clone of the same controlled Gitea repository.

A

Feature Developer

Implements the required feature using a separate branch and meaningful commits.

B

Test Developer

Adds required tests and records failures through a test branch and Pull Request.

C

Code Reviewer

Reviews both Pull Requests, requests changes and verifies the revised work.

02

Start from an assigned issue

The issue defines the task, role and acceptance criteria. GitStack stores the Gitea issue identifier and later checks that the Pull Request links back to it.

ISSUE #15 · FEATURE DEVELOPER

Add password visibility control

  • Create feature/password-toggle
  • Make at least two focused commits
  • Link Issue #15 in the Pull Request
  • Do not merge before tests and review
03

Create the required branch and commits

Feature Developer terminal
$ git switch -c feature/password-toggle
$ git add login.html
$ git commit -m "Add password visibility button"
$ git add login.js
$ git commit -m "Implement password toggle functionality"
$ git push -u origin feature/password-toggle
✓ Branch and two meaningful commits published

আপনি সরাসরি main branch-এ commit করেছেন। Team mission-এর জন্য assigned feature branch তৈরি করে সেখানে কাজ করুন।

04

Open a complete Pull Request

GitStack uses the real Gitea Pull Request interface. The frontend shows mission instructions, links and activity summaries instead of rebuilding Gitea’s review system.

OPEN

Add password visibility control

feature/password-toggle → main

Description

Adds a password visibility button and toggle behavior.

Related issue

Closes #15

Testing

Manual behavior verified. Automated tests pending from Issue #16.

05

Review and request changes

The reviewer checks requirements, commit quality, tests and merge readiness. Approval before required tests pass is treated as an incorrect workflow.

CHANGES REQUESTED

Required test is missing

The toggle works, but the mission requires automated coverage. Please add or link the test Pull Request before merging.

DEVELOPER RESPONSE

Updated after review

Linked the Test Developer’s Pull Request and updated the implementation to satisfy the failed edge case.

APPROVED

Ready after tests pass

Requirements are complete, the requested change was addressed and CI is green.

06

Use automated tests before approval

Gitea checks
# Pull Request checks
✓ lint
✓ password-toggle tests
✓ build
All required checks passed

Merge discipline

The reviewer should not approve and the developer should not merge until all required checks pass.

07

Resolve the controlled team conflict

The prepared repository deliberately creates one predictable conflict so the team can demonstrate the same assessment scenario.

Terminal
$ git merge test/password-toggle
CONFLICT (content): Merge conflict in login.js
$ git status
both modified: login.js
1

Preserve both requirements

Keep the feature behavior and test-compatible logic.

2

Remove markers

Delete all conflict markers from the final file.

3

Run tests and merge

Only complete the merge when the test suite passes.
